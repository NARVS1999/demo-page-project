## Interaction & State Patterns

1. **Booking flow state machine (locked):** `idle` (no service → helper hint) → `service chosen` (calendar renders) → `slot selected` (confirm bar appears; pill becomes primary) → `dialog open` → `submitting` (buttons disabled + `Loader2`) → `success` (toast "Booking confirmed." → `router.push("/booking/{id}")`) | `conflict` (destructive Alert in dialog → dialog closes → slot list refreshes via `router.refresh()` → selected slot cleared → back to `slot selected`-eligible) | `payment failed` (destructive Alert, dialog stays open, retryable). Changing the service at any point clears the selected slot.
2. **Blocking mutations (inherited):** never optimistic — server action returns `{ok: true}` or an error payload; pending states disable submit; server errors surface as destructive Alerts inside the dialog (never only a toast); success → toast + navigation. Rationale unchanged: demo apps are judged on correctness.
3. **Double-booking truth:** the conflict Alert IS the UI face of the atomic `UPDATE slots … WHERE booked_at IS NULL` rowcount check (CONTEXT decision) — it must read as "just taken", not "you failed", and must offer the refreshed list as the next step.
4. **Deposit flow:** checkbox inside the dialog, default unchecked. Checked → server action calls `createPayment({ amount, currency: "usd" })` inside the same transaction as the slot claim; failure aborts the whole booking (no partial state — no slot claimed, no payment row, "No charge was made"). Refund on any cancel path (user or admin) — toast suffix "Deposit refunded.".
5. **Login gating (locked):** public browsing never gates; slot *selection* by a guest redirects to `/login?next=/book` (existing Phase 0 session pattern). After login the flow resumes with the preselected service? No — redirect lands on `/book` fresh (service selection is one click; keeping `?service=` in `next` is allowed if trivial: `next=/book?service={slug}`). Keep it simple: `next=/book`.
6. **User cancel (confirmation page):** alert-dialog → destructive confirm → toast ("Booking cancelled." ± deposit suffix) → `router.refresh()` → page shows cancelled badge, cancel button disappears. Cancelled slot reopens for others (server-side, invisible to this user).
7. **Admin confirm/cancel:** per-row actions; Confirm only on `pending` rows, Cancel on `pending`/`confirmed` rows — no other action combos exist (locked status model: pending → confirmed → cancelled). Both mutate via server action + refresh; cancelled slots reopen.
8. **Toast vs inline (inherited):** inline destructive Alerts for conflict/payment/server errors; toasts ONLY for success confirmations. One toast per event — the deposit refund never fires a second toast.
9. **Filters:** GET form (server-rendered, shareable URL, no client fetch — identical to Phase 1 search pattern); count line pluralizes ("1 booking" / "N bookings"); "Clear filters" shown only when a filter is active.
10. **Slot availability rule:** a slot renders `taken` when a non-cancelled booking exists on it (pending AND confirmed both block the slot; cancelled frees it). Rendered server-side per fetch — no client mutation of availability outside `router.refresh()` after conflict.

## Accessibility

All Phase 0/1 rules inherited (focus rings, contrast ≥ 4.5:1, one H1 per page, labeled inputs, Radix dialogs, 40×40 targets, landmarks, reduced motion, `lang="en"`). Phase 2 additions:

1. **Service cards:** parent `role="radiogroup"` + `aria-label="Choose a service"`; cards `role="radio"` `aria-checked`, arrow-key navigation (left/right/up/down), `Tab` moves into and out of the group only (Phase 1 segmented-control pattern).
2. **Slot pills:** `<button>`s — selected `aria-pressed="true"`; taken `disabled` (removed from tab order) + `aria-label="{time} — taken"`; available pills `aria-label="{time} — available"` (state is announced, never color-only).
3. **Date groups:** each day `<h2>` (visible dateline header) — page H1 "Book a slot" is the only H1; no skipped levels.
4. **Confirm dialog:** Radix dialog (focus trap, `aria-modal`, ESC dismiss, overlay click dismiss — inherited); focus lands on the first summary row; conflict/payment Alerts are `role="alert"` and focus follows the Alert inside the dialog.
